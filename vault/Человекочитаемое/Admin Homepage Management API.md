# Admin Homepage Management API

Заметка фиксирует реализованный контракт управления подборками главной страницы. Источник истины для кода - backend `apps/api`, frontend `apps/front` и миграции DbUp.

## Назначение

Административный API управляет заранее созданными секциями главной страницы и их элементами. Публичный API отдает только активные и видимые секции для витрины.

## Endpoints

### Admin

Базовый путь: `/api/admin/homepage/sections`.

- `GET /api/admin/homepage/sections` - возвращает все фиксированные секции и их элементы для админки.
- `PUT /api/admin/homepage/sections/{id}` - обновляет заголовок, лимит элементов, сортировку и активность секции.
- `POST /api/admin/homepage/sections/{id}/items` - добавляет в секцию один товар или одну категорию.
- `PUT /api/admin/homepage/sections/{id}/items/order` - переупорядочивает элементы секции списком `itemIds`.
- `PUT /api/admin/homepage/sections/{id}/items/{itemId}` - обновляет сортировку и активность элемента.
- `DELETE /api/admin/homepage/sections/{id}/items/{itemId}` - удаляет элемент секции.

### Public

- `GET /api/public/homepage/sections` - возвращает активные секции главной страницы с публично видимыми элементами.

Другие HTTP-методы публичного пути не являются частью контракта.

## Роли и доступ

- Admin endpoints требуют авторизованную cookie-сессию.
- Доступ к admin endpoints разрешен только ролям `seller` и `admin`.
- Остальные роли получают отказ доступа.
- Public endpoint не требует авторизации.

## CSRF

- Все admin-мутации требуют заголовок `X-CSRF-Token`.
- Токен должен совпадать с CSRF claim текущей cookie-сессии.
- `GET /api/admin/homepage/sections` не требует CSRF-заголовок, но требует авторизованную staff-сессию.
- Public endpoint не требует CSRF-заголовок.

## Видимость на публичной главной

Публичный ответ включает только:

- активные секции `homepage_sections.is_active = TRUE`;
- активные элементы `homepage_section_items.is_active = TRUE`;
- товары с `products.is_active = TRUE`;
- товары со статусом публикации `publish_status = 'published'`;
- товары с непустым `slug`;
- товары, у которых основная категория активна;
- категории с `categories.is_active = TRUE`;
- категории с непустым `slug`.

Публичный ответ применяет `item_limit` секции после сортировки элементов. Admin API показывает элементы с вычисленным `visibilityStatus`, чтобы редактор видел причины непопадания элемента на витрину.

## Фиксированные секции

Секции создаются миграцией и идентифицируются стабильным `code`.

| Code | Тип | Назначение |
| --- | --- | --- |
| `hero_products` | `product_list` | Главные товары первого экрана |
| `featured_products` | `product_list` | Популярные позиции |
| `direction_categories` | `category_list` | Направления каталога |

Поддерживаемые типы секций:

- `product_list` - элементы секции должны ссылаться на товары.
- `category_list` - элементы секции должны ссылаться на категории.

Элемент секции всегда указывает ровно на одну сущность: либо `productId`, либо `categoryId`.

## Ограничения и валидация

- `itemLimit` нормализуется в диапазон от 1 до 24.
- Переупорядочивание принимает непустой список уникальных `itemIds`.
- Нельзя добавить элемент без цели или одновременно с товаром и категорией.
- Несовместимые элементы и тип секции отклоняются ограничениями БД и сервисным слоем.
- Не найденная секция или элемент возвращают 404.
- Некорректная мутация возвращает ошибку `admin_catalog.invalid_request`.

## Вне scope

- Создание и удаление самих секций через API.
- Изменение `code` или `type` секции через API.
- Публикация товара, управление slug и активностью товара или категории.
- Загрузка изображений, файловое хранилище и импорт каталога.
- SEO/GEO-метаданные страниц каталога, кроме влияния публичной видимости на главную.
- Персонализация главной страницы под пользователя или регион.
