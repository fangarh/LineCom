# Структура данных релиза

## Контекст

Этот документ фиксирует продуктовую структуру данных релизной версии LineCom. Он не является финальной физической схемой БД, но задает сущности, связи и ограничения, которые нужно учитывать при проектировании backend, API, админки, Excel-импорта и SEO-каталога.

Основа: каталог-заявочная модель без публичных цен и онлайн-оплаты. Складской и 1С-контуры должны быть заложены расширяемо, но включаются как отдельные рабочие модули.

## Общие принципы

- Товар имеет одну основную категорию.
- Дополнительные SEO-срезы делаются через посадочные страницы по фильтрам, а не через множественные категории товара.
- Характеристики товаров типизированные и задаются на уровне категории.
- Фильтры, сравнение и SEO опираются на структурные характеристики.
- Продажа кабеля идет только целыми бухтами или коробками, без метража и резки.
- Публичная цена не хранится как обязательное отображаемое поле релизной версии. На сайте показывается `Цена по запросу`.
- Публичный статус наличия задается вручную: `В наличии`, `Под заказ`, `Уточнить`.
- Быстрый заказ создает обычную заявку с отдельным источником, а не отдельную коммерческую сущность.
- Excel-импорт не должен автоматически создавать хаос в каталоге. Нужна форма сопоставления колонок, категорий, характеристик и значений.

## Категории

`Category` - дерево категорий каталога.

Основные поля:

- id;
- parentId;
- name;
- slug;
- description;
- seoTitle;
- seoDescription;
- h1;
- sortOrder;
- isActive;
- isVisibleInMenu.

Категория определяет:

- набор характеристик;
- фильтруемые характеристики;
- характеристики для сравнения;
- характеристики, важные для SEO и названия;
- базовый контекст Excel-шаблона.

Товар принадлежит одной основной категории через `Product.primaryCategoryId`.

## Товары

`Product` - основная товарная сущность.

Основные поля:

- id;
- primaryCategoryId;
- name;
- slug;
- sku;
- externalId;
- brandId;
- description;
- shortDescription;
- availabilityStatus;
- saleUnit;
- unitQuantity;
- publishStatus;
- seoTitle;
- seoDescription;
- h1;
- sortOrder;
- createdAt;
- updatedAt.

`availabilityStatus`:

- `in_stock` - публично `В наличии`;
- `on_order` - публично `Под заказ`;
- `check_availability` - публично `Уточнить`.

`saleUnit`:

- `coil` - бухта;
- `box` - коробка;
- `piece` - штука;
- `pack` - упаковка.

`unitQuantity` хранит человеко- и машинно-понятное количество в единице продажи. Например, `305 м`, `100 шт`, `1 шт`.

Для релизной версии как публичного каталога-заявочной системы не нужны:

- цена;
- скидки;
- онлайн-оплата;
- публичные остатки по складам;
- резка по метражу;
- резервирование.

## Изображения товара

`ProductImage` - изображения товара.

Поля:

- id;
- productId;
- filePath или mediaId;
- alt;
- title;
- sortOrder;
- isMain.

Изображения используются в карточке товара, списке товаров, сравнении и заявке.

## Бренды и производители

`Brand` - бренд или производитель.

Поля:

- id;
- name;
- slug;
- description;
- seoTitle;
- seoDescription;
- logoPath или mediaId;
- isActive.

Бренд может быть необязательным для конкретного товара, но поле должно быть частью релизной структуры, потому что бренд часто участвует в фильтрах, SEO и сравнении.

## Характеристики категорий

`CategoryAttribute` - определение характеристики внутри категории.

Поля:

- id;
- categoryId;
- name;
- code;
- type;
- unit;
- isRequired;
- isFilterable;
- isComparable;
- isVisibleInProduct;
- isSeoImportant;
- isUsedInGeneratedName;
- sortOrder;
- isActive.

Типы характеристик релизной версии:

- `text`;
- `number`;
- `select`;
- `boolean`.

Расширяемые типы, которые модель не должна блокировать:

- `range`;
- `multi_select`;
- `decimal_with_unit`;
- `json`.

Для `select`-характеристик значения должны храниться как справочник.

## Значения характеристик

`ProductAttributeValue` - значение характеристики конкретного товара.

Поля:

- id;
- productId;
- attributeId;
- valueText;
- valueNumber;
- valueBoolean;
- optionId;
- normalizedValue;

Для каждого товара значение должно соответствовать типу характеристики.

`AttributeOption` - справочник значений для `select`-характеристик.

Поля:

- id;
- attributeId;
- value;
- slug;
- normalizedValue;
- sortOrder;
- isActive.

Примеры:

- `CU`;
- `CCA`;
- `F/UTP`;
- `U/UTP`;
- `Indoor`;
- `Outdoor`;
- `Cat 5e`.

## Синонимы значений

`AttributeValueAlias` - синонимы и варианты написания значений для Excel-импорта.

Поля:

- id;
- attributeId;
- optionId;
- alias;
- normalizedAlias.

Примеры:

- `медь`, `CU`, `Cu`, `Медный`;
- `омедненный алюминий`, `CCA`;
- `наружная`, `OUTDOOR`, `для внешней прокладки`.

Эта сущность нужна, чтобы импорт из разных файлов не плодил дубли значений.

## Посадочные страницы по фильтрам

`LandingPage` - SEO-посадочная страница на основе категории и нормализованных условий фильтра.

Поля:

- id;
- categoryId;
- name;
- slug;
- h1;
- seoTitle;
- seoDescription;
- introText;
- bottomText;
- canonicalUrl;
- indexMode;
- isActive;
- sortOrder.

Условия выборки хранятся не в JSONB, а в нормализованных таблицах. Это нужно для ссылочной целостности, отладки, SEO-контроля и поиска посадочных страниц, которые используют конкретные характеристики.

`LandingPageFilterGroup` - группа условий посадочной страницы.

Поля:

- id;
- landingPageId;
- parentGroupId;
- logicalOperator;
- sortOrder.

`logicalOperator`:

- `and`;
- `or`.

`LandingPageFilterCondition` - конкретное условие фильтра.

Поля:

- id;
- groupId;
- attributeId;
- targetField;
- operator;
- optionId;
- valueText;
- valueNumber;
- valueBoolean;
- sortOrder.

`attributeId` используется для условий по характеристикам. `targetField` используется для условий по базовым полям товара, например `brandId`, `availabilityStatus`, `saleUnit`.

`operator`:

- `equals`;
- `not_equals`;
- `in`;
- `contains`;
- `greater_than`;
- `less_than`;
- `between`;
- `exists`.

Для условий по `select`-характеристикам используется `optionId`. Для числовых, текстовых и boolean-условий используются соответствующие value-поля.

Пример условий:

- категория: `Витая пара`;
- `категория кабеля = Cat 5e`;
- `применение = наружная прокладка`;
- `материал проводника = медь`.

Посадочная страница не является второй категорией товара. Товар попадает на нее автоматически, если соответствует условиям фильтра.

Не каждый фильтр должен индексироваться. Индексация включается явно через `indexMode`.

## Сравнение товаров

Сравнение товаров строится на основе структурных характеристик.

Для первой релизной версии постоянный список сравнения можно хранить на frontend в сессии или localStorage. Релизная структура должна не мешать добавить серверное хранение сравнения для зарегистрированных пользователей через `ProductComparisonList`.

Базовые правила:

- сравниваются товары одной основной категории;
- сравнение использует характеристики с `isComparable = true`;
- цена не участвует в сравнении;
- из сравнения можно перейти к товару или добавить товар в заявку.

Расширение для серверного хранения сравнения:

`ProductComparisonList`:

- id;
- userId;
- categoryId;
- createdAt;
- updatedAt.

`ProductComparisonItem`:

- id;
- comparisonListId;
- productId;
- sortOrder;

## Пользователи

`User` - зарегистрированный клиент или сотрудник.

Поля:

- id;
- name;
- email;
- phone;
- passwordHash;
- role;
- isActive;
- createdAt;
- updatedAt.

Роли релизной версии:

- `customer`;
- `admin`;
- `seller`.

Вход в релизной версии:

- email или телефон;
- пароль.

Одноразовые коды не входят в релизный способ входа, но модель не должна мешать добавить их отдельным способом аутентификации.

## Организации

`Organization` - необязательная карточка организации клиента.

Поля:

- id;
- userId;
- name;
- inn;
- contactPerson;
- phone;
- email;
- comment;
- createdAt;
- updatedAt.

В первой релизной версии у пользователя может быть одна организация. Роли внутри организации, несколько организаций на пользователя и сложная B2B-иерархия не включаются как рабочая функция, но модель не должна блокировать их добавление отдельным расширением.

## Заявки

`Request` - коммерческая заявка покупателя.

Поля:

- id;
- number;
- numberYear;
- numberSequence;
- userId;
- source;
- status;
- customerNameSnapshot;
- customerEmailSnapshot;
- customerPhoneSnapshot;
- organizationNameSnapshot;
- organizationInnSnapshot;
- organizationContactPersonSnapshot;
- customerComment;
- internalComment;
- createdAt;
- updatedAt.

`source`:

- `cart`;
- `quick_order`;
- `admin_created`.

`status`:

- `new` - `Новая`;
- `in_progress` - `В работе`;
- `completed` - `Завершено`;
- `cancelled` - `Отменено`.

Формат номера заявки:

- шаблон: `ЗКYY-0001`;
- пример для 2026 года: `ЗК26-0001`;
- `YY` - последние две цифры года создания;
- числовая часть - порядковый номер внутри года;
- счетчик сбрасывается каждый год;
- номер генерируется backend внутри транзакции;
- для защиты от гонок используется отдельная таблица `RequestNumberCounter`.

`RequestNumberCounter`:

- id;
- year;
- lastSequence;
- updatedAt.

Ограничения:

- `Request.number` уникален;
- `Request.numberYear + Request.numberSequence` уникальны.

Быстрый заказ создает обычную заявку с `source = quick_order`.

Заявки не закрепляются за конкретным менеджером.

## Позиции заявки

`RequestItem` - позиция заявки.

Поля:

- id;
- requestId;
- productId;
- productNameSnapshot;
- productSkuSnapshot;
- saleUnitSnapshot;
- unitQuantitySnapshot;
- quantity;
- customerComment;
- sortOrder.

В позиции нужно сохранять снимок основных товарных данных на момент заявки, чтобы история заявки не менялась при последующем редактировании товара.

`quantity` - количество единиц продажи, а не метраж.

## История заявки

`RequestHistory` - история изменений заявки.

Поля:

- id;
- requestId;
- actorUserId;
- eventType;
- oldValue;
- newValue;
- comment;
- createdAt.

Минимально нужно фиксировать:

- создание заявки;
- смену статуса;
- изменение внутреннего комментария;
- изменение состава позиций, если оно разрешено в админке.

## Excel-импорт

`ImportJob` - запуск импорта.

Поля:

- id;
- fileName;
- status;
- totalRows;
- createdRows;
- updatedRows;
- skippedRows;
- errorRows;
- createdByUserId;
- createdAt;
- completedAt.

`ImportMapping` - сохраненное сопоставление колонок.

Поля:

- id;
- name;
- categoryId;
- mappingDefinition;
- createdByUserId;
- createdAt;
- updatedAt.

`mappingDefinition` хранит соответствие колонок Excel:

- базовым полям товара;
- категории;
- характеристикам;
- статусу наличия;
- единице продажи;
- количеству в единице;
- SEO-полям;
- внешнему идентификатору.

Импорт должен давать форму сопоставления и настройки:

- выбрать существующую категорию или создать новую;
- выбрать существующую характеристику или создать новую;
- выбрать тип характеристики;
- сопоставить значения справочников;
- создать недостающие значения;
- сохранить сопоставление для повторного использования;
- показать предпросмотр результата перед применением.

## Ошибки импорта

`ImportRowError` - ошибка строки импорта.

Поля:

- id;
- importJobId;
- rowNumber;
- columnName;
- errorCode;
- message;
- rawValue.

Импорт не должен автоматически публиковать сомнительные товары без подтверждения оператора.

## Идентификация товаров при импорте

Приоритет обновления существующего товара:

1. `externalId`, если он есть.
2. `sku`, артикул или код.
3. `название + категория` только как кандидат для ручного сопоставления.

Автоматически обновлять товар по одному названию нельзя.

## Excel-экспорт

Экспорт должен уметь выгружать:

- базовые поля товара;
- категорию;
- бренд;
- статус наличия;
- единицу продажи;
- количество в единице;
- характеристики;
- SEO-поля;
- признак публикации;
- externalId и sku.

Желательно поддержать экспорт по категории, по фильтру и по результатам поиска.

## Складской контур

Складской учет не включается как рабочий контур первой релизной версии, но структура должна быть совместима с его добавлением без перестройки каталога и заявок.

Заложенные сущности складского контура:

`Warehouse`:

- id;
- name;
- address;
- isActive.

`InventoryBalance`:

- id;
- productId;
- warehouseId;
- quantity;
- reservedQuantity;
- updatedAt.

`ReorderRule`:

- id;
- productId;
- minQuantity;
- targetQuantity;
- supplierId.

Эти сущности не включаются как рабочие функции без отдельного решения, но считаются целевым направлением расширения.

## Контур 1С-интеграции

Прямая синхронизация с 1С не входит в первую релизную версию как рабочий модуль.

Для интеграции нужно сразу заложить:

- `externalId` у товара;
- `sku`;
- снимки товарных и клиентских данных в заявках;
- возможность сопоставления значений характеристик;
- возможность хранить внешние идентификаторы категорий, клиентов, организаций и заявок, если это потребуется.

## Открытые технические решения

Следующие вопросы относятся уже к проектированию backend и БД:

- точный состав индексов после первых реальных фильтров каталога;
- точная структура DTO каждого модуля перед его реализацией;
- точный набор кодов ошибок API и импорта;
- точная политика PostgreSQL full-text search после появления реального каталога.
