# Архитектура backend и БД

## Контекст

Этот документ фиксирует релизные архитектурные решения для backend и базы данных LineCom.

Основа проекта:

- backend: ASP.NET Core Web API;
- база данных: PostgreSQL;
- frontend: Next.js;
- продуктовая модель: каталог-заявочная система без публичных цен и онлайн-оплаты;
- структура данных: см. `Структура данных релиза.md`.

## Архитектурный стиль

Backend строится как модульный монолит в одном приложении `apps/api`.

Причины:

- один деплой и одна база данных;
- достаточно простая эксплуатация;
- четкие границы предметных модулей;
- возможность развивать сложный каталог, заявки, импорт и админку без преждевременного дробления на сервисы.

Микросервисная архитектура не используется.

## Модули backend

Основные модули:

- `Catalog` - категории, товары, бренды, изображения;
- `Attributes` - характеристики, значения, справочники, синонимы;
- `Seo` - посадочные страницы, sitemap, canonical-данные;
- `Requests` - заявки, позиции заявок, история;
- `Customers` - клиенты и организации;
- `ImportExport` - Excel-импорт, Excel-экспорт, маппинги, ошибки;
- `Auth` - регистрация, вход, выход, роли, сессии;
- `Files` - локальное файловое хранилище;
- `Admin` не является отдельным доменом, а выражается через API-маршруты и права доступа поверх предметных модулей.

Рекомендуемая структура `apps/api`:

```text
apps/api/
  Modules/
    Catalog/
      Models/
      DTOs/
      Controllers/
      Repositories/
      Services/
      Sql/
    Attributes/
    Seo/
    Requests/
    Customers/
    ImportExport/
    Auth/
    Files/
  Infrastructure/
    Database/
      DbConnectionFactory.cs
      Transactions/
      Migrations/
    Security/
    Storage/
  Shared/
    Kernel/
    Errors/
    Pagination/
    Validation/
```

Модуль держит предметные модели, DTO, контроллеры, сервисы, репозитории и SQL рядом. Общая инфраструктура вынесена отдельно.

## Доступ к данным

Entity Framework не используется.

Принятая связка:

- `Npgsql` - PostgreSQL driver;
- `Dapper` - маппинг результатов SQL-запросов;
- `DbUp` - SQL-миграции.

Принципы:

- писать явный SQL;
- использовать только параметризованные запросы;
- не использовать универсальный generic repository;
- для каждого модуля держать собственные repositories/query services;
- для сложных чтений каталога, фильтров, сравнения и посадочных страниц использовать отдельные SQL-запросы;
- для транзакционных операций использовать `NpgsqlConnection` и `NpgsqlTransaction`;
- не смешивать SQL-строки с контроллерами.

## Подключение к PostgreSQL

Подключение к БД строится через `NpgsqlDataSource`.

`DbConnectionFactory` отвечает за:

- доступ к `NpgsqlDataSource`;
- открытие соединений;
- создание команд или выдачу открытого `NpgsqlConnection`;
- единый способ работы с connection string.

Пулы соединений использует Npgsql.

## Миграции

Миграции выполняются через DbUp.

Подход:

- миграции пишутся как SQL-скрипты;
- скрипты хранятся в `Infrastructure/Database/Migrations`;
- имя скрипта содержит порядковый номер и описание;
- DbUp ведет журнал примененных миграций;
- миграции применяются отдельной командой или раннером, а не неявно из бизнес-логики.

Пример именования:

```text
001_init.sql
002_catalog_tables.sql
003_attributes_tables.sql
004_requests_tables.sql
```

Преимущество SQL-миграций: полный контроль над PostgreSQL DDL, индексами, constraints, partial indexes и JSONB.

## Правило качества

Архитектура проектируется как релизная, а не как временная MVP-заготовка.

Намеренный технический долг не допускается. Если компромисс все же принимается отдельным решением, он должен быть явно описан: причина, риск, условие пересмотра и владелец решения.

Перед завершением архитектурной, проектной или кодовой задачи обязательно проверять:

- нет ли временных решений, выданных за релизные;
- нет ли незафиксированных допущений;
- нет ли TODO/TBD без решения;
- не перенесена ли обязательная целостность данных только в приложение, если ее можно закрепить в БД;
- не ухудшены ли SEO/GEO, безопасность, мигрируемость и сопровождаемость.

## Характеристики товаров

Характеристики товаров хранятся нормализованно.

Основные таблицы:

- `category_attributes`;
- `attribute_options`;
- `attribute_value_aliases`;
- `product_attribute_values`.

`product_attribute_values` использует несколько типовых колонок:

- `value_text`;
- `value_number`;
- `value_boolean`;
- `attribute_option_id`;
- `normalized_value`.

Заполнена должна быть только колонка, соответствующая типу характеристики.

Правила:

- тип значения проверяется на уровне БД и в приложении;
- для `select`-характеристик используется `attribute_options`;
- для Excel-синонимов используется `attribute_value_aliases`;
- JSONB не используется для товарных характеристик.

На уровне БД должны быть constraints, которые не позволяют сохранить несовместимое значение характеристики:

- `text` заполняет только `value_text`;
- `number` заполняет только `value_number`;
- `boolean` заполняет только `value_boolean`;
- `select` заполняет только `attribute_option_id`;
- для одной характеристики товара не может быть несколько активных значений, если характеристика не является множественной;
- `attribute_option_id` должен ссылаться на значение той же характеристики, что и `attribute_id`.

Так как обычный CHECK constraint не может ссылаться на другую таблицу, соответствие типа характеристики и заполненной value-колонки нужно закрепить через PostgreSQL trigger/function или другой строгий механизм БД, а не оставлять только на уровне приложения.

Индексы:

- `product_attribute_values(product_id)`;
- `product_attribute_values(attribute_id)`;
- `product_attribute_values(attribute_option_id)`;
- `product_attribute_values(attribute_id, value_number)`;
- `product_attribute_values(attribute_id, normalized_value)`;
- уникальность `product_id + attribute_id` для одиночных характеристик.

## Номера заявок

Номер заявки имеет формат:

```text
ЗКYY-0001
```

Пример:

```text
ЗК26-0001
```

Правила:

- `ЗК` - постоянный префикс;
- `YY` - последние две цифры года создания;
- числовая часть - порядковый номер внутри года;
- счетчик сбрасывается каждый год;
- номер генерируется только backend;
- генерация выполняется внутри транзакции;
- для генерации используется таблица `request_number_counters`;
- в `requests` хранятся `number`, `number_year`, `number_sequence`;
- `number` уникален;
- пара `number_year + number_sequence` уникальна.

Генерация не должна строиться через `max(number_sequence) + 1` по таблице заявок, потому что это создает гонки при параллельном создании.

## Посадочные страницы

Условия посадочных страниц хранятся нормализованно, не в JSONB.

Основные таблицы:

- `landing_pages`;
- `landing_page_filter_groups`;
- `landing_page_filter_conditions`.

Причины:

- нужны внешние ключи на характеристики и значения;
- нужно понимать, какие посадочные страницы зависят от конкретной характеристики;
- это важный SEO-контур, где нельзя прятать условия в непрозрачный JSON;
- проще отлаживать и индексировать.

`landing_page_filter_conditions` поддерживает условия по:

- характеристикам товара;
- базовым полям товара: бренд, статус наличия, единица продажи и т.п.

## JSONB

JSONB используется только для служебных конфигураций, где структура действительно является настройкой формы или процесса.

Разрешенный кейс:

- `ImportMapping.mappingDefinition`.

Правила для JSONB:

- хранить `schemaVersion`;
- валидировать структуру на уровне приложения;
- не хранить в JSONB основную товарную модель;
- не хранить в JSONB SEO-критичные условия посадочных страниц.

## API

API делится по аудитории и уровню доступа.

Маршруты:

- `/api/public/...` - публичный каталог, категории, товары, посадочные страницы, сравнение, заявки без входа;
- `/api/account/...` - профиль клиента, организация, история заявок, повтор заявки;
- `/api/admin/...` - управление каталогом, характеристиками, товарами, брендами, посадочными страницами, заявками, пользователями, Excel-импортом и экспортом;
- `/api/auth/...` - регистрация, вход, выход, CSRF, текущая сессия.

Swagger/OpenAPI группируется тегами по аудитории и модулю:

- `Public Catalog`;
- `Public Requests`;
- `Account Requests`;
- `Admin Products`;
- `Admin Attributes`;
- `Admin Import`;
- `Auth`.

Первичный уровень детализации API-контрактов:

- публичный каталог: listing DTO, detail DTO, filters DTO;
- публичные заявки: create request DTO, quick order DTO;
- кабинет клиента: profile DTO, organization DTO, account request DTO;
- админка каталога: category edit DTO, product edit DTO, attribute edit DTO, landing page edit DTO;
- админка заявок: admin request list DTO, admin request detail DTO, status update DTO;
- импорт/экспорт: upload DTO, mapping DTO, preview DTO, apply DTO, import errors DTO.

Полный OpenAPI-контракт расписывается перед реализацией соответствующего модуля. Это не считается техническим долгом, если для каждого модуля перед реализацией фиксируются DTO, ошибки, права доступа и сценарии валидации.

## Авторизация и сессии

Релизный подход: HttpOnly cookie auth.

Правила:

- вход по email или телефону и паролю;
- auth cookie имеет `HttpOnly`;
- cookie должна иметь `Secure`;
- `SameSite` настраивается под фактическое размещение frontend и API;
- JavaScript на frontend не хранит access token;
- роли: `customer`, `seller`, `admin`;
- доступ контролируется через authorization policies.

Публичные endpoints каталога доступны без входа. Кабинет требует пользователя `customer`. Админка требует `seller` или `admin`.

## CSRF

Так как используется cookie-auth, для небезопасных методов нужна CSRF-защита.

Подход:

- auth cookie остается `HttpOnly`;
- CSRF token выдается отдельным endpoint или отдельной cookie;
- frontend отправляет CSRF token в заголовке;
- `POST`, `PUT`, `PATCH`, `DELETE` требуют CSRF-заголовок;
- `GET` не должен менять состояние;
- logout тоже требует CSRF.

## Файлы

Файлы хранятся локально на сервере. Это релизный целевой вариант, а не временная замена S3/MinIO.

Корневая папка задается настройкой, например `Storage:RootPath`.

Структура:

```text
storage/
  products/
  imports/
  exports/
  temp/
```

Общая сущность:

`StoredFile`:

- id;
- storageKey;
- originalFileName;
- contentType;
- size;
- checksum;
- purpose;
- status;
- createdByUserId;
- createdAt.

Связи:

- `ProductImage` ссылается на `StoredFile`;
- `ImportJob` ссылается на исходный `StoredFile`;
- экспорт может ссылаться на `StoredFile`.

Правило: файлы удаляются и заменяются только через backend, чтобы БД и диск не расходились.

Политика удаления:

- физическое удаление файла не выполняется напрямую при удалении товара, изображения, импорта или экспорта;
- `StoredFile.status`: `active`, `deleted`, `orphaned`;
- бизнес-сущности отвязывают файл или переводят его в удаленное состояние;
- физическая очистка выполняется отдельной служебной операцией;
- очистка удаляет только файлы без ссылок, со статусом `deleted` или `orphaned`, старше заданного срока;
- базовый срок удержания перед физическим удалением: 30 дней;
- система должна уметь диагностировать расхождения: запись есть в БД, но файла нет на диске; файл есть на диске, но записи нет в БД.

## Excel-импорт и экспорт

Excel-контур работает через мастер сопоставления.

Поток импорта:

1. Загрузка файла.
2. Чтение заголовков и первых строк.
3. Настройка сопоставления колонок.
4. Создание недостающих категорий, характеристик и значений через форму.
5. Предпросмотр результата.
6. Валидация.
7. Применение импорта.
8. Отчет об ошибках и изменениях.

`ImportMapping.mappingDefinition` хранится в JSONB, потому что это настройка процесса импорта.

Обновление товара при импорте:

1. `externalId`;
2. `sku`;
3. `название + категория` только как кандидат для ручного сопоставления.

## Транзакции

Транзакции обязательны для операций, которые меняют несколько связанных сущностей:

- создание заявки с позициями и историей;
- изменение заявки с записью истории;
- применение Excel-импорта;
- создание товара с характеристиками и изображениями;
- изменение категории вместе с характеристиками.

Транзакционная граница должна быть в application service, а не в контроллере.

## Ошибки и валидация

Контроллеры не должны содержать предметную валидацию.

Подход:

- DTO валидируются на входе;
- доменные правила проверяются в сервисах;
- ошибки возвращаются в едином формате;
- ошибки импорта сохраняются построчно в `ImportRowError`;
- публичный API не должен раскрывать внутренние исключения.

## Поиск и фильтрация

Фильтры каталога строятся SQL-запросами по нормализованным значениям характеристик.

Поиск по тексту можно начать с PostgreSQL `ILIKE` и индексов, но структура должна не мешать перейти на PostgreSQL full-text search для названий, описаний, артикулов и характеристик.

SEO-посадочные страницы используют тот же механизм фильтрации, что и публичный каталог, но условия берутся из нормализованных таблиц посадочных страниц.

## Неиспользуемые подходы

Не используются:

- Entity Framework;
- EF migrations;
- микросервисы;
- S3/MinIO как целевой файловый контур;
- хранение товарных характеристик в JSONB;
- хранение SEO-фильтров посадочных страниц в JSONB.
