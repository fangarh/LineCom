# Auth + Request Core design

## Назначение

Этап `Auth + Request Core` добавляет минимальный релизный контур пользователя и коммерческой заявки. Заявка создается только авторизованным пользователем, потому что принято решение сразу строить заявки на учетной записи клиента, а не на анонимном контакте.

Цель этапа: дать backend-основу для регистрации, входа, профиля, необязательной организации и заявок без публичных цен и онлайн-оплаты.

## Границы этапа

Входит в этап:

- регистрация клиента по email или телефону и паролю;
- вход по email или телефону и паролю;
- получение текущего пользователя;
- хранение ролей `customer`, `seller`, `admin`;
- профиль клиента;
- необязательная организация клиента;
- создание заявки авторизованным клиентом;
- список заявок текущего клиента;
- карточка заявки текущего клиента;
- генерация номера заявки формата `ЗКYY-0001`;
- снимки контактных, организационных и товарных данных на момент создания заявки;
- история создания заявки.

Не входит в этап:

- одноразовые коды входа;
- восстановление пароля;
- email/SMS-уведомления;
- личный кабинет на frontend;
- админская смена статусов заявок;
- редактирование состава заявки продавцом;
- онлайн-оплата;
- счета, отгрузки и интеграция с 1С;
- складской расчет дефицита и дозаказа.

Эти контуры не блокируются моделью, но проектируются и реализуются отдельными этапами.

## Модули backend

Добавляются два backend-модуля:

- `Auth` - регистрация, вход, текущий пользователь, роли и пароли;
- `Requests` - заявки, позиции, номера и история.

Модули следуют текущей структуре `apps/api/Modules/*`:

- `Controllers` принимают HTTP-запросы и не содержат SQL;
- `DTOs` фиксируют внешний контракт;
- `Commands` или `Services` выполняют сценарии записи;
- `Queries` выполняют чтение через Dapper;
- SQL остается параметризованным;
- доступ к PostgreSQL идет через общий `IDbConnectionFactory`;
- Entity Framework не используется.

## Данные

### Users

`users` хранит учетные записи клиентов и сотрудников.

Основные поля:

- `id`;
- `name`;
- `email`;
- `phone`;
- `password_hash`;
- `role`;
- `is_active`;
- `created_at`;
- `updated_at`.

Ограничения:

- хотя бы одно из полей `email` или `phone` обязательно;
- `email` уникален среди непустых значений;
- `phone` уникален среди непустых значений;
- `role` ограничен значениями `customer`, `seller`, `admin`;
- пароль никогда не хранится в открытом виде.

### Organizations

`organizations` хранит необязательную карточку организации пользователя.

Основные поля:

- `id`;
- `user_id`;
- `name`;
- `inn`;
- `contact_person`;
- `phone`;
- `email`;
- `comment`;
- `created_at`;
- `updated_at`.

В релизной версии у пользователя может быть одна организация. Это ограничение фиксируется уникальностью `user_id`, но не мешает позже перейти к нескольким организациям через отдельную миграцию модели.

### Requests

`requests` хранит коммерческие заявки.

Основные поля:

- `id`;
- `number`;
- `number_year`;
- `number_sequence`;
- `user_id`;
- `source`;
- `status`;
- `customer_name_snapshot`;
- `customer_email_snapshot`;
- `customer_phone_snapshot`;
- `organization_name_snapshot`;
- `organization_inn_snapshot`;
- `organization_contact_person_snapshot`;
- `customer_comment`;
- `internal_comment`;
- `created_at`;
- `updated_at`.

`source`:

- `cart`;
- `quick_order`;
- `admin_created`.

`status`:

- `new`;
- `in_progress`;
- `completed`;
- `canceled`.

На этом этапе клиент создает заявку со статусом `new`. Смена статуса сотрудником проектируется следующим этапом.

### RequestNumberCounters

`request_number_counters` защищает генерацию номеров от гонок.

Основные поля:

- `id`;
- `year`;
- `last_sequence`;
- `updated_at`.

Номер создается внутри транзакции:

1. определяется год заявки;
2. строка счетчика года блокируется для обновления;
3. `last_sequence` увеличивается на 1;
4. создается номер `ЗКYY-0001`;
5. заявка сохраняется с уникальными `number` и парой `number_year + number_sequence`.

### RequestItems

`request_items` хранит позиции заявки.

Основные поля:

- `id`;
- `request_id`;
- `product_id`;
- `product_name_snapshot`;
- `product_sku_snapshot`;
- `sale_unit_snapshot`;
- `unit_quantity_snapshot`;
- `quantity`;
- `customer_comment`;
- `sort_order`.

`quantity` - количество единиц продажи, не метраж.

При создании заявки backend читает опубликованные товары из активных категорий и сохраняет снимок данных. Если товар не найден или не проходит публичную видимость, заявка не создается.

### RequestHistory

`request_history` хранит историю событий заявки.

На этом этапе обязательно фиксируется событие:

- `created` - заявка создана клиентом.

Структура сразу поддерживает дальнейшие события:

- `status_changed`;
- `internal_comment_changed`;
- `items_changed`.

## API

### Auth API

`POST /api/auth/register`

Регистрирует клиента. Принимает имя, email или телефон, пароль. Возвращает пользователя и auth-состояние.

`POST /api/auth/login`

Выполняет вход по email или телефону и паролю.

`GET /api/auth/me`

Возвращает текущего пользователя.

### Customer Requests API

Все endpoints заявок требуют авторизованного пользователя.

`POST /api/account/requests`

Создает заявку текущего пользователя.

Тело запроса содержит:

- `source`;
- позиции с `productId`, `quantity`, `customerComment`;
- `customerComment`;
- при необходимости снимок или выбор текущей организации из профиля.

`GET /api/account/requests`

Возвращает список заявок текущего пользователя.

`GET /api/account/requests/{number}`

Возвращает карточку заявки текущего пользователя по номеру. Пользователь не может получить чужую заявку.

## Auth-подход

Для релизного backend-этапа нужен серверный механизм авторизации, пригодный для frontend и будущей админки.

Принятый подход:

- password hash через стандартный безопасный алгоритм платформы;
- авторизация через серверную HTTP-only cookie;
- cookie помечается `Secure`, `HttpOnly`, `SameSite=Lax` для production-сценария;
- изменяющие endpoints, включая создание заявки, должны быть совместимы с CSRF-защитой;
- контроллеры заявок не доверяют user id из тела запроса, а берут пользователя только из auth-контекста;
- роли проверяются на уровне API, где это требуется;
- будущие одноразовые коды добавляются как отдельный способ входа, не заменяя текущую модель пользователя.

Bearer token не используется как основной способ входа в релизном web-сценарии, чтобы не перекладывать хранение токена на frontend. Если позже появится отдельный внешний API или мобильное приложение, bearer token проектируется отдельным контуром.

## Ошибки

Ошибки возвращаются через единый `ApiErrorResponse`.

Базовые коды этапа:

- `auth.invalid_credentials`;
- `auth.user_already_exists`;
- `auth.user_inactive`;
- `auth.unauthorized`;
- `auth.forbidden`;
- `request.invalid_items`;
- `request.product_not_available`;
- `request.not_found`;
- `request.invalid_status`;
- `internal_error`.

Внутренние exception messages не попадают в публичный ответ.

## Проверки целостности

Обязательные проверки при создании заявки:

- пользователь авторизован и активен;
- в заявке есть минимум одна позиция;
- количество каждой позиции больше нуля;
- товар существует, опубликован и находится в активной категории;
- количество относится к единицам продажи товара;
- контактные данные пользователя позволяют обработать заявку;
- номер заявки генерируется только backend внутри транзакции;
- снимки товара, контактов и организации сохраняются до завершения транзакции.

## Тестирование

Минимальное покрытие этапа:

- миграция создает таблицы, ограничения и индексы;
- регистрация требует email или телефон;
- регистрация не допускает дубль email или телефона;
- пароль не хранится открытым текстом;
- вход отклоняет неверный пароль;
- успешный вход устанавливает auth cookie;
- `GET /api/auth/me` требует auth и возвращает текущего пользователя;
- создание заявки требует auth;
- создание заявки генерирует номер `ЗКYY-0001`;
- параллельная генерация номеров не создает дубликаты;
- создание заявки сохраняет снимки данных товара и клиента;
- чужая заявка недоступна клиенту;
- список заявок ограничен текущим пользователем;
- все контролируемые ошибки возвращаются через `ApiErrorResponse`.

## Технический долг

В этом дизайне нет намеренных временных решений. Ограничения этапа зафиксированы явно и не подменяют релизную модель:

- одноразовые коды, восстановление пароля и уведомления вынесены в отдельные этапы;
- смена статусов заявок сотрудником вынесена в следующий этап;
- bearer token вынесен за пределы релизного web-сценария и не смешивается с cookie-auth в этом этапе;
- анонимные заявки не поддерживаются, потому что принято решение создавать заявки сразу на пользователя.
