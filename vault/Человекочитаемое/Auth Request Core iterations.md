# Auth + Request Core iterations

## Назначение

Этот план разбивает этап `Auth + Request Core` на маленькие проверяемые итерации.

Цель этапа: получить релизную backend-основу для регистрации, входа, профиля, необязательной организации и коммерческих заявок, где заявка создается только авторизованным пользователем.

Основа этапа зафиксирована в заметке `Auth Request Core design.md`.

## Общие правила этапа

- Источник данных - PostgreSQL через `Npgsql` и `Dapper`.
- Entity Framework не используется.
- Миграции пишутся SQL-скриптами и выполняются через DbUp.
- SQL-запросы параметризованы.
- Контроллеры не содержат SQL и предметную логику.
- Ошибки возвращаются через единый формат `ApiErrorResponse`.
- Заявки создаются только авторизованным пользователем.
- Auth строится на HTTP-only cookie.
- Пароль не хранится в открытом виде.
- Номер заявки генерируется только backend внутри транзакции.
- Публичные цены, онлайн-оплата, счета, отгрузки и 1С не входят в этот этап.
- После каждой кодовой итерации выполняются `dotnet build` и `dotnet test`.
- После изменения API, схемы данных или важных границ поведения обновляется Obsidian.
- Перед закрытием каждой итерации проверяется отсутствие намеренного технического долга.

## Итерация 1: Контракт Auth + Requests

Зафиксировать API-контракт до реализации кода.

Результат:

- заметка `Auth Request Core API.md`;
- endpoints auth: регистрация, вход, текущий пользователь;
- endpoints заявок: создать заявку, список своих заявок, карточка своей заявки;
- DTO запросов и ответов;
- коды ошибок;
- правила cookie-auth и CSRF-совместимости;
- границы этапа без восстановления пароля, уведомлений, админской смены статусов и анонимных заявок.

Критерии завершения:

- контракт можно читать без знания кода;
- все ошибки имеют публичный code и message;
- в контракте нет публичных цен и онлайн-оплаты;
- дальнейшая реализация не требует менять продуктовые границы этапа.

## Итерация 2: База пользователей и организаций

Добавить миграцию для учетных записей и необязательных организаций без поведения API.

Результат:

- таблица `users`;
- таблица `organizations`;
- роли `customer`, `seller`, `admin`;
- ограничение: хотя бы один контакт `email` или `phone`;
- уникальность непустых `email` и `phone`;
- одна организация на пользователя в релизной версии;
- тесты миграции.

Критерии завершения:

- миграция применима через DbUp;
- ограничения проверяются тестами;
- пароль хранится только как `password_hash`;
- структура не использует Entity Framework.

## Итерация 3: Регистрация клиента

Реализовать создание клиента.

Результат:

- `POST /api/auth/register`;
- email или телефон обязателен;
- пароль хешируется;
- дубль email или phone запрещен;
- роль по умолчанию `customer`;
- успешная регистрация устанавливает auth-состояние согласно контракту;
- тесты успешной регистрации и контролируемых ошибок.

Критерии завершения:

- пароль не возвращается и не хранится открытым текстом;
- дубль контактов возвращает `auth.user_already_exists`;
- невалидные входные данные возвращают контролируемую ошибку;
- регистрация не создает организацию без явного ввода данных организации.

## Итерация 4: Вход и текущий пользователь

Закрыть минимальный auth-контур.

Результат:

- `POST /api/auth/login`;
- HTTP-only auth cookie;
- `GET /api/auth/me`;
- проверка активности пользователя;
- ошибки `auth.invalid_credentials`, `auth.unauthorized`, `auth.user_inactive`;
- тесты cookie-auth.

Критерии завершения:

- неверный пароль не раскрывает, какой контакт существует;
- неактивный пользователь не получает доступ;
- `GET /api/auth/me` без auth возвращает `auth.unauthorized`;
- auth-контекст является единственным источником `userId` для защищенных endpoints.

## Итерация 5: Профиль и организация

Дать данные, из которых потом создается снимок заявки.

Результат:

- чтение текущего профиля;
- создание или обновление необязательной организации;
- валидация базовых полей организации;
- тесты принадлежности организации текущему пользователю.

Критерии завершения:

- пользователь видит только свой профиль;
- организация принадлежит только текущему пользователю;
- обновление организации не меняет исторические заявки;
- одна организация на пользователя соблюдается ограничениями БД и кодом.

## Итерация 6: База заявок и генератор номера

Подготовить надежную запись заявок.

Результат:

- таблица `requests`;
- таблица `request_items`;
- таблица `request_history`;
- таблица `request_number_counters`;
- транзакционная генерация номера `ЗКYY-0001`;
- уникальность `requests.number`;
- уникальность пары `number_year + number_sequence`;
- тесты миграции и генератора номера.

Критерии завершения:

- номер создается только backend;
- счетчик года защищен от дублей;
- числовая часть начинается с `0001` для нового года;
- структура сохраняет снимки контактов, организации и товаров.

## Итерация 7: Создание заявки

Реализовать основной коммерческий сценарий.

Результат:

- `POST /api/account/requests`;
- endpoint требует авторизованного пользователя;
- в заявке минимум одна позиция;
- `quantity > 0`;
- товар должен быть опубликован и находиться в активной категории;
- сохраняются снимки товара, контактов и организации;
- создается история `created`;
- статус заявки `new`;
- тесты успешного создания и контролируемых ошибок.

Критерии завершения:

- заявка создается в одной транзакции с номером, позициями и историей;
- товарные снимки не зависят от будущего редактирования товара;
- `userId` берется только из auth-контекста;
- ошибка по недоступному товару возвращается как `request.product_not_available`.

## Итерация 8: Заявки текущего пользователя

Дать клиенту чтение своих заявок.

Результат:

- `GET /api/account/requests`;
- `GET /api/account/requests/{number}`;
- пользователь видит только свои заявки;
- карточка возвращает позиции, снимки, статус и историю создания;
- тесты прав доступа и `request.not_found`.

Критерии завершения:

- чужая заявка не раскрывается и возвращает `request.not_found`;
- список заявок ограничен текущим пользователем;
- карточка заявки не требует внутренних id в URL;
- ответ не содержит публичных цен.

## Итерация 9: Финальная сверка этапа

Сверить реализацию с Obsidian и закрыть этап.

Результат:

- актуальная заметка `Auth Request Core API.md`;
- список реализованных endpoints;
- зафиксированные границы этапа;
- `dotnet build`;
- `dotnet test`;
- проверка на отсутствие TODO/TBD, временных решений и незакрытых требований.

Критерии завершения:

- реализация соответствует `Auth Request Core design.md`;
- все итерации имеют статус;
- все обязательные проверки выполнены свежими командами;
- следующая точка развития выбрана отдельно: админская обработка заявок, frontend auth/request flow или другой утвержденный этап.

## Рекомендуемая точка продолжения

После очистки контекста начать с итерации 1: создать заметку `Auth Request Core API.md` с контрактом auth API и customer requests API.
