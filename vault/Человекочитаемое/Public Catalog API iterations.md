# Public Catalog API iterations

## Назначение

Этот план разбивает этап `Public Catalog read API` на маленькие проверяемые итерации.

Цель этапа: получить публичный read-only API каталога поверх PostgreSQL, Npgsql и Dapper без временных решений, с учетом SEO/GEO и будущих фильтров, сравнения, заявок и frontend-страниц.

## Общие правила этапа

- Источник данных - PostgreSQL через `Npgsql` и `Dapper`.
- Entity Framework не используется.
- SQL-запросы параметризованы.
- Публичный API показывает только опубликованные товары, активные категории, активные бренды и активные характеристики.
- Публичная цена не добавляется и не возвращается.
- Контроллеры не содержат SQL и предметную логику.
- Ошибки возвращаются через единый формат `ApiErrorResponse`.
- После каждой кодовой итерации выполняются `dotnet build` и `dotnet test`.
- После изменения API или важных границ поведения обновляется Obsidian.

Статус: реализовано.

## Итерaция 3: Категории

Реализовать первый рабочий endpoint:

```text
GET /api/public/catalog/categories
```

Результат:

- чтение активных категорий;
- сортировка по `parent_id`, `sort_order`, `name`;
- DTO для публичного списка или дерева категорий;
- тест endpoint-а.

Статус: реализовано.

Реализация:

- endpoint `GET /api/public/catalog/categories` реализован в публичном контроллере каталога;
- чтение выполняется через `IPublicCategoryQuery` и Dapper поверх `IDbConnectionFactory`;
- SQL выбирает только `is_active = true` категории и сортирует по `parent_id`, `sort_order`, `name`, `slug`;
- ответ строится как `PublicCategoryTreeResponse` с вложенными `children`;
- endpoint покрыт тестами на успешный JSON-ответ, camelCase-контракт и запрет `POST`.

## Итерaция 4: Категория по slug

Реализовать endpoint:

```text
GET /api/public/catalog/categories/{slug}
```

Результат:

- SEO-поля категории;
- публичные поля категории;
- `404` через единый формат ошибок;
- тесты на успешный ответ и `not_found`.

Статус: реализовано.

Реализация:

- endpoint `GET /api/public/catalog/categories/{slug}` реализован в публичном контроллере категорий;
- detail-чтение добавлено в `IPublicCategoryQuery` и Dapper-реализацию;
- SQL параметризован по `@Slug`, выбирает только активную категорию и активные breadcrumbs;
- `seo.title`, `seo.description` и `canonicalPath` формируются для публичной категории;
- отсутствие категории или нарушение публичной видимости возвращает `404 catalog.category_not_found`;
- endpoint и detail-builder покрыты тестами на успешный ответ, breadcrumbs, SEO и `not_found`.

## Итерaция 5: Список товаров

Реализовать endpoint:

```text
GET /api/public/catalog/products?categorySlug=...
```

Результат:

- список опубликованных товаров;
- базовые поля товара: `name`, `slug`, `sku`, бренд, статус наличия, единица продажи, количество в единице;
- главное изображение;
- без фильтров по характеристикам на этой итерации;
- тесты.

Статус: реализовано.

Реализация:

- endpoint `GET /api/public/catalog/products` реализован в публичном контроллере товаров;
- чтение выполняется через `IPublicProductQuery` и Dapper поверх `IDbConnectionFactory`;
- SQL возвращает только `publish_status = 'published'` товары из активных категорий;
- неактивные бренды не публикуются и попадают в ответ как `brand = null`;
- главное изображение выбирается только через активный `stored_files.status = 'active'` файл назначения `product_image`;
- реализованы `categorySlug`, `brandSlug`, `availabilityStatus`, `saleUnit`, `page`, `pageSize`, `sort`;
- `attribute.*` фильтры на этой итерации отклоняются как `400 catalog.invalid_filter`;
- неизвестная или неактивная категория в `categorySlug` возвращает `404 catalog.category_not_found`;
- endpoint, parser, SQL-контракт и response-builder покрыты тестами.

Реализовать endpoint:


Результат:

- фильтруемые характеристики категории;
- options для `select`-характеристик;
- подготовка к фильтрации списка товаров;
- тесты.

Статус: реализовано.

Реализация:

- endpoint `GET /api/public/catalog/categories/{slug}/filters` реализован в публичном контроллере категорий;
- чтение выполняется через `IPublicCategoryQuery` и Dapper поверх `IDbConnectionFactory`;

- endpoint, SQL-контракт и response-builder покрыты тестами.

## Итерaция 8: Минимальная фильтрация списка товаров

Расширить endpoint:

```text
GET /api/public/catalog/products?categorySlug=...&attribute=...
```

Результат:

- фильтрация по `select`-характеристикам;
- затем отдельно можно расширить фильтрацию на `boolean`, `number` и `text`;
- SQL остается явным и параметризованным;
- тесты на фильтрацию.

Статус: реализовано.

Реализация:

- parser `GET /api/public/catalog/products` принимает query-параметры вида `attribute.{code}=optionSlug`;
- пустой код характеристики, пустое значение или несколько значений одного attribute-фильтра возвращают `400 catalog.invalid_filter`;
- Dapper-реализация добавляет для каждого attribute-фильтра отдельное параметризованное `EXISTS`-условие;
- фильтрация ограничена активными, фильтруемыми характеристиками типа `select` и активными options;
- фильтр применяется к характеристикам основной категории товара через `attribute.category_id = product.primary_category_id`;
- неизвестная характеристика, неактивная option или характеристика неподдерживаемого типа не публикуют товар в результате фильтра;
- поддержка `boolean`, `number` и `text` остается отдельным расширением следующего этапа;
- parser, endpoint-передача фильтров и SQL-контракт покрыты тестами.
