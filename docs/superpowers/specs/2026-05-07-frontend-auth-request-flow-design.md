# Frontend Auth + Request Flow Design

## Назначение

Первый frontend-срез LineCom реализует вертикальный коммерческий путь покупателя: публичный каталог ведет к товару, товар добавляется в черновик заявки, при отправке пользователь проходит регистрацию или вход, заполняет профиль и организацию при необходимости, отправляет заявку и видит ее в личном кабинете.

Срез проверяет уже реализованный backend-контракт `Auth + Request Core` на реальном пользовательском сценарии и не расширяет backend без отдельного решения.

## Выбранный подход

Выбран вариант `A. Коммерческий путь от каталога`.

Публичный каталог остается главным входом в сценарий. Auth, профиль, организация и личный кабинет подключаются по мере движения к заявке, а не становятся самостоятельным центром первого среза.

Причины выбора:

- backend регистрации, входа, профиля, организации и заявок уже реализован и проверен;
- фронт сейчас находится в состоянии стартового Next.js-шаблона, поэтому нужен первый рабочий пользовательский путь;
- сценарий `каталог -> товар -> заявка -> вход/регистрация -> отправка -> мои заявки` проверяет коммерческую ценность end-to-end;
- подход не уводит срез в админку, импорт Excel, цены, оплату или интеграции.

Отклоненные варианты:

- `Account-first`: удобен для разработки кабинета, но главный покупательский путь становится вторичным.
- `Wizard-first`: полезен для сложной заявки, но добавляет лишнюю механику до проверки каталога и базовой заявки.
- `Catalog-only`: хорошо для SEO/GEO, но откладывает проверку готового backend-контура заявок.

## Маршруты

Публичные маршруты:

- `/` - рабочая витрина и вход в каталог, без маркетинговой landing page как основного экрана;
- `/catalog` - обзор каталога;
- `/catalog/[categorySlug]` - категория, список товаров и минимальные фильтры по данным public catalog API;
- `/products/[slug]` - карточка товара с действием добавления в заявку;
- `/request` - черновик коммерческой заявки;
- `/auth/login` - вход;
- `/auth/register` - регистрация.

Account-маршруты:

- `/account/profile` - профиль пользователя и необязательная организация;
- `/account/requests` - список заявок текущего пользователя;
- `/account/requests/[number]` - карточка заявки по публичному номеру.

В URL публичного каталога используются slug, а не внутренние id. Карточка заявки использует публичный номер заявки, а не внутренний id.

## UX-Принципы

LineCom не является классическим магазином с публичной ценой и оплатой на сайте. UI должен использовать язык заявки:

- `заявка`, а не `заказ`;
- `отправить заявку`, а не `оформить заказ`;
- `добавить в заявку`, а не `купить`;
- `Цена по запросу`, без числовых публичных цен;
- `количество единиц продажи`, а не произвольный метраж.

UI не должен обещать онлайн-оплату, доставку, счет, отгрузку или автоматическую фиксацию заказа.

## Архитектура Next.js

Frontend использует Next.js App Router.

Публичные SEO/GEO-страницы каталога и товаров:

- реализуются как server-rendered pages;
- получают данные из public catalog API;
- формируют metadata на сервере из SEO-полей категории или товара;
- сохраняют индексируемый контент доступным без клиентского состояния;
- используют slug-based маршруты.

Интерактивные области:

- черновик заявки;
- формы login/register;
- account-профиль;
- организация;
- список и карточка заявок;
- обработка form state, loading, validation и backend errors.

Эти части реализуются через client components там, где нужны события браузера, localStorage или интерактивные формы.

## API-Слой

В `apps/front` добавляется тонкий typed API client:

- отдельный client для public catalog API;
- отдельный client для auth/account/request API;
- единая обработка `ApiErrorResponse`;
- без предметной логики внутри React-компонентов;
- публичные catalog fetch и приватные account fetch не смешиваются.

Публичные catalog fetch могут использовать server rendering и подходящий cache/revalidate режим. Приватные account/auth/request fetch используют динамическое поведение и не должны кэшироваться как публичный контент.

## Черновик Заявки

Черновик заявки хранится на frontend в `localStorage` или клиентском state с восстановлением после перезагрузки.

Позиция черновика содержит:

- `productId`;
- `slug` или ссылку для возврата к карточке;
- `productName` для отображения;
- `productSku`;
- `saleUnit`;
- `unitQuantity`;
- `quantity`;
- `customerComment`.

Frontend-черновик не является источником истины для исторических снимков. При отправке backend заново валидирует товар, проверяет публикацию и активную категорию, генерирует номер, сохраняет собственные snapshots и историю.

Поведение черновика:

- добавление товара из списка или карточки;
- изменение количества;
- комментарий к позиции;
- общий комментарий заявки;
- удаление позиции;
- пустое состояние;
- сохранение при перезагрузке;
- очистка или предложение очистить после успешной отправки.

## Auth И CSRF

Auth строится на существующем HTTP-only cookie backend-контракте. Frontend не читает значение cookie.

После `POST /api/auth/login`, `POST /api/auth/register` или `GET /api/auth/me` frontend хранит в runtime state:

- публичный `CurrentUserDto`;
- `csrfToken`.

Изменяющие защищенные запросы отправляют заголовок `X-CSRF-Token`.

Если пользователь не авторизован при отправке заявки:

1. frontend сохраняет текущий черновик;
2. перенаправляет на login/register;
3. после успешного входа возвращает пользователя к `/request`;
4. отправка заявки остается явным действием пользователя.

При `403 auth.forbidden` для изменяющего запроса frontend один раз выполняет `GET /api/auth/me`, обновляет `csrfToken` и повторяет запрос. Если повторный запрос снова возвращает `403`, показывается контролируемое сообщение о недостатке прав или необходимости повторного входа.

## UI-Состав

Каталог:

- дерево или список категорий;
- список товаров;
- название, SKU, статус наличия, единица продажи, количество в единице;
- `Цена по запросу`;
- минимальные фильтры только по уже доступному backend-контракту;
- действие добавления товара в заявку.

Карточка товара:

- H1/название;
- описание;
- характеристики;
- изображение при наличии;
- статус наличия;
- единица продажи и количество в единице;
- `Цена по запросу`;
- добавление в заявку.

Заявка:

- позиции;
- количество;
- комментарий к позиции;
- общий комментарий;
- удаление позиции;
- отправка заявки;
- success-состояние с номером заявки и ссылкой на карточку заявки.

Auth/account:

- login;
- register;
- профиль пользователя;
- необязательная организация;
- список заявок;
- карточка заявки со snapshots, позициями, статусом и историей создания.

## Ошибки И Состояния

Поддерживаемые состояния:

- loading;
- empty;
- validation error;
- controlled backend error;
- unauthorized redirect;
- forbidden;
- product unavailable;
- request creation success.

Ошибки backend показываются через публичные `code` и `message` из `ApiErrorResponse`. Сырые exception messages не отображаются.

Особые случаи:

- `auth.unauthorized`: перенаправить на вход или регистрацию с возвратом к исходному сценарию;
- `auth.forbidden`: один раз обновить CSRF через `GET /api/auth/me`, затем повторить изменяющий запрос;
- `request.product_not_available`: оставить позицию в черновике, подсветить ее и предложить удалить или вернуться к товару;
- `request.not_found`: показать контролируемое состояние отсутствующей заявки.

## Границы Среза

Входит:

- frontend public catalog flow на существующем public catalog API;
- frontend auth flow на существующем auth API;
- профиль и организация;
- черновик заявки;
- создание заявки авторизованным пользователем;
- список и карточка своих заявок;
- SEO/GEO-совместимая структура публичных страниц;
- обработка CSRF и контролируемых API-ошибок.

Не входит:

- публичные цены;
- онлайн-оплата;
- счета;
- доставка;
- отгрузки;
- интеграция с 1С;
- восстановление пароля;
- одноразовые коды;
- уведомления;
- анонимные заявки;
- админская смена статусов;
- редактирование заявки продавцом;
- новый backend для фильтров, если текущий public catalog API этого не поддерживает;
- полноценный Excel-import UI.

## Проверки

Критерии завершения:

- пользователь проходит путь `каталог -> товар -> заявка -> регистрация/вход -> отправка -> карточка заявки`;
- публичные страницы используют slug URL, server-rendered content и metadata;
- auth работает через HTTP-only cookie без чтения cookie на frontend;
- изменяющие защищенные запросы используют `X-CSRF-Token`;
- ошибки backend показываются контролируемо;
- UI не содержит публичных цен, оплаты или языка классического оформления заказа;
- черновик заявки не теряется при перезагрузке;
- `.superpowers/` не попадает в git.

Команды проверки:

```powershell
npm.cmd run lint
npm.cmd run build
dotnet build LineCom.sln -m:1
dotnet test LineCom.sln -m:1
```

Обычный параллельный `dotnet build LineCom.sln` в текущем окружении нестабилен и падает без ошибок при обходе project references. До отдельного исправления окружения проверочная команда для .NET использует `-m:1`.

## Риски

- Если текущий public catalog API не покрывает нужные данные для качественного списка товаров или карточки, срез должен ограничиться доступным контрактом, а расширение backend проектируется отдельно.
- Если cookie-auth и CSRF требуют proxy/API route на стороне Next.js для стабильной same-origin работы, это нужно явно заложить в implementation plan.
- Если реальные изображения товаров отсутствуют, UI должен иметь аккуратное состояние без изображения, не создавая ложные placeholder-продукты.
- Если frontend-тестовый стек отсутствует, нужно решить в плане реализации, добавлять ли его в этом срезе или ограничиться lint/build и browser QA.

## Открытые Решения Для Плана Реализации

- Точный способ соединения frontend и backend в dev: прямой API base URL или Next.js rewrites/proxy.
- Точный frontend state library: начать с React state/context и localStorage либо добавить специализированное хранилище.
- Нужен ли frontend test runner в первом срезе.
- Какой минимальный визуальный стиль принять для LineCom на базе существующего логотипа и ассетов.
