# Admin Full Catalog UX Design

## Статус

Согласовано с пользователем 2026-05-13.

Документ фиксирует следующий срез улучшений админского интерфейса LineCom: навигация администрирования, полный рабочий список товаров, дерево категорий, удобное наполнение главной, автоматический slug и смена пароля текущего пользователя.

## Контекст

В проекте уже есть:

- админские маршруты `/admin/requests`, `/admin/catalog`, `/admin/homepage`;
- backend на PostgreSQL, Npgsql и Dapper;
- SQL-миграции через DbUp;
- админские API каталога и главной под `/api/admin`;
- публичный каталог и SEO/GEO-маршруты на slug URL;
- cookie-auth и CSRF-защита для изменяющих защищённых запросов.

Текущие UX-проблемы:

- `Заявки клиентов`, `Каталог админки` и `Главная админки` перегружают верхнюю навигацию и должны быть объединены в `Администрирование`;
- на `/admin/homepage` добавление товара или категории по UUID неудобно;
- на `/admin/catalog` список товаров показывает только часть данных без очевидной пагинации или подгрузки;
- товарная строка слишком крупная для рабочего списка;
- в списке товаров не хватает быстрых признаков активности, публикации и привязанной категории;
- категории удобнее вести деревом, включая выбор родителя;
- slug должен генерироваться автоматически, но оставаться редактируемым;
- нужна смена пароля только для текущего пользователя.

## Цели

- Сделать `Администрирование` единым выпадающим пунктом для staff-пользователей.
- Сохранить разделение маршрутов: заявки, каталог и главная остаются отдельными страницами.
- Сделать список товаров компактным, табличным и полным через явную пагинацию.
- Показать в списке товаров активность, статус публикации, готовность и наличие категории.
- Сделать категории древовидными в списке и при выборе родителя.
- Заменить ввод UUID на главной поиском по товарам и категориям.
- Автоматически генерировать slug из названия с ручным переопределением.
- Добавить смену пароля текущего пользователя через защищённый backend endpoint.

## Не входит

- Управление пользователями.
- Админская смена пароля другого пользователя.
- Восстановление пароля по email/SMS.
- Одноразовые коды входа.
- Audit log изменений каталога.
- Массовые операции над товарами.
- Excel-импорт или экспорт.
- Изменение публичных URL, sitemap, robots, canonical или публичной SEO/GEO-логики.
- Перенос товаров при перемещении категории.

## Выбранный подход

Выбран вариант `B`: полный рабочий каталог.

Реализация идёт как один продуктовый срез, но технически разбивается на последовательные этапы:

1. навигация `Администрирование` и компактные списки с пагинацией;
2. дерево категорий и выбор родителя из дерева;
3. поиск товаров/категорий при наполнении главной;
4. автоматическая генерация slug;
5. смена пароля текущего пользователя.

Такой порядок закрывает пользовательскую боль без оставления намеренного долга. При этом он учитывает текущий размер frontend-файлов: `admin-category-manager.tsx` и `admin-homepage-manager.tsx` уже крупные, поэтому перед добавлением поведения нужна узкая декомпозиция.

## Навигация

Верхняя навигация получает один staff-пункт `Администрирование`.

Для ролей `seller` и `admin` пункт раскрывает:

- `Заявки клиентов` -> `/admin/requests`;
- `Каталог админки` -> `/admin/catalog`;
- `Главная админки` -> `/admin/homepage`.

Для `customer` и анонимного пользователя пункт не показывается. Frontend-видимость не считается защитой: backend-авторизация остаётся обязательной.

На мобильном экране `Администрирование` раскрывается внутри существующего мобильного меню, без отдельной страницы-лендинга.

## Товары В Админке

Раздел `Товары` в `/admin/catalog` переходит от крупных карточек к компактной таблице.

Таблица показывает:

- название;
- slug;
- SKU или externalId, если есть;
- категорию;
- бренд;
- активность;
- статус публикации;
- готовность к публикации;
- краткий признак проблем: нет категории, нет slug, нет SEO, неактивная категория.

Список должен иметь явную пагинацию:

- текущая страница;
- размер страницы;
- общее количество товаров;
- кнопки `Назад` и `Дальше`;
- состояние `1-60 из N`.

Поиск и фильтры сохраняются:

- поиск по названию, SKU, externalId и slug;
- категория;
- бренд;
- активность;
- статус публикации.

Выбор строки открывает существующий редактор товара. Редактор остаётся полноразмерным рабочим контуром с вкладками.

## Категории

Раздел `Категории` получает дерево.

Дерево показывает:

- корневые категории;
- дочерние категории;
- активность;
- видимость в меню;
- количество товаров;
- количество дочерних категорий.

Выбор категории в дереве открывает редактор справа или ниже, в зависимости от ширины экрана.

Выбор родителя при создании, редактировании и перемещении категории также выполняется из дерева. Плоский длинный `select` не используется как основной интерфейс.

Правила безопасности:

- категория не может стать родителем самой себе;
- категория не может стать дочерней для своего потомка;
- backend остаётся источником истины по запрету циклов;
- перемещение категории не меняет категорию уже существующих товаров;
- физическое удаление категории остаётся запрещённым, если она используется.

## Главная Админки

На `/admin/homepage` добавление элемента секции больше не требует ручного UUID.

Для секций типа `product_list` используется поиск товаров:

- по названию;
- SKU;
- externalId;
- slug.

Для секций типа `category_list` используется поиск категорий:

- по названию;
- slug.

Результат поиска показывает:

- тип элемента;
- название;
- slug;
- SKU/externalId для товара;
- активность;
- статус публикации товара;
- публичную видимость или причину, почему элемент не попадёт на витрину.

Добавление по-прежнему отправляет ID в существующий backend contract, но пользователь работает с поиском и понятными результатами.

## Автоматический Slug

Slug генерируется автоматически из названия для:

- товара;
- категории;
- бренда;
- option у select-характеристики, если этот сценарий уже редактируется в UI.

Правила:

- при создании slug заполняется автоматически после ввода названия;
- пока пользователь не изменил slug вручную, изменение названия обновляет slug;
- после ручного изменения slug считается закреплённым и не перетирается автоматикой;
- рядом со slug показывается действие `Сгенерировать заново`;
- backend нормализует и валидирует slug перед сохранением;
- конфликт slug возвращает существующую ошибку `admin_catalog.slug_already_exists`;
- UI показывает понятное сообщение и предлагает изменить slug.

Генерация должна поддерживать русские названия через транслитерацию и очистку:

- нижний регистр;
- пробелы и разделители в `-`;
- удаление недопустимых символов;
- схлопывание повторяющихся `-`;
- обрезка крайних `-`.

Автоматическое добавление числового суффикса допускается только если backend сможет подтвердить уникальность. Если такой проверки нет в текущем API, первый срез показывает конфликт и предлагает ручное исправление.

## Смена Пароля

Смена пароля нужна только текущему пользователю.

Новый backend endpoint:

- `PUT /api/account/password`.

Тело запроса:

```json
{
  "currentPassword": "old-password",
  "newPassword": "new-secure-password"
}
```

Правила:

- endpoint требует авторизованного активного пользователя;
- endpoint требует CSRF;
- текущий пароль обязателен;
- новый пароль обязателен;
- длина нового пароля от 8 до 128 символов;
- новый пароль хешируется текущим `IPasswordHasher`;
- неверный текущий пароль возвращает контролируемую ошибку;
- пароль не возвращается в API;
- после успешной смены текущая сессия может остаться активной.

Frontend:

- форма размещается в личном кабинете рядом с профилем;
- поля: текущий пароль, новый пароль, повтор нового пароля;
- несовпадение нового пароля и повтора проверяется на клиенте;
- submit отправляет только `currentPassword` и `newPassword`;
- успешное сохранение показывает короткое подтверждение.

Админского сброса пароля другого пользователя в этом срезе нет.

## Архитектура Frontend

Перед добавлением нового поведения нужно разложить крупные компоненты:

- `AdminCategoryManager` разделить на контейнер данных, дерево, форму категории и блок перемещения;
- `AdminHomepageManager` разделить на контейнер данных, список секций, редактор секции, поиск и список элементов;
- товарный список вынести в табличный компонент с пагинацией;
- чистую логику дерева, построения списков и slug вынести в helper-модули с unit-тестами.

Состояние контейнеров должно отвечать за:

- загрузку данных;
- фильтры;
- пагинацию;
- выбранную запись;
- мутации;
- защиту от устаревших async-ответов.

Презентационные компоненты отвечают только за рендер и локальные UI-события.

## Backend И API

Для списка товаров и категорий существующие admin endpoints уже поддерживают `page`, `pageSize`, фильтры и total-поля. UI должен начать использовать эти поля явно.

Для поиска на главной предпочтительно использовать существующие endpoints:

- `GET /api/admin/catalog/products`;
- `GET /api/admin/catalog/categories`.

Если существующих полей ответа не хватит для публичной видимости в результатах поиска главной, backend можно расширить минимально, не меняя публичные API.

Для смены пароля потребуется новый account endpoint, сервисный метод и тесты. Entity Framework не используется.

## Ошибки И Состояния

Нужны контролируемые состояния:

- загрузка списка;
- пустой результат;
- ошибка загрузки;
- ошибка мутации;
- устаревшая CSRF-сессия;
- slug занят;
- неверный текущий пароль;
- товар или категория не подходят для публичной главной;
- выбранная категория больше недоступна после обновления дерева.

Ошибки должны использовать существующий формат `ApiErrorResponse`.

## SEO/GEO Влияние

Срез затрагивает внутренние защищённые страницы и не должен менять:

- публичные маршруты категорий и товаров;
- генерацию sitemap;
- robots;
- canonical;
- metadata публичного каталога;
- публичный контент страниц.

Автоматический slug влияет на будущие публичные URL товаров и категорий, поэтому:

- slug остаётся видимым и редактируемым до публикации;
- изменение slug существующей опубликованной сущности должно быть осознанным ручным действием;
- UI не должен скрывать последствия изменения slug.

## Тестирование

Backend:

- `PUT /api/account/password` требует auth;
- endpoint требует CSRF;
- неверный текущий пароль отклоняется;
- новый пароль валидируется по длине;
- успешная смена обновляет hash и позволяет войти с новым паролем;
- старый пароль после смены не подходит;
- пароль не возвращается в ответах.

Frontend unit/component:

- `Администрирование` показывается только `seller` и `admin`;
- выпадающее меню содержит заявки, каталог и главную;
- список товаров запрашивает и отображает page/pageSize/total;
- переключение страниц сохраняет фильтры;
- строка товара показывает активность, категорию и готовность;
- дерево категорий строится из плоского списка;
- выбор родителя через дерево исключает текущую категорию и её потомков;
- поиск на главной добавляет товар без ручного ввода UUID;
- slug генерируется из русского и латинского названия;
- ручное изменение slug отключает автоперезапись;
- форма смены пароля проверяет совпадение нового пароля.

Browser QA:

- desktop и mobile навигация с `Администрирование`;
- `/admin/catalog` товары: фильтры, пагинация, выбор товара;
- `/admin/catalog` категории: дерево, редактирование, выбор родителя;
- `/admin/homepage`: поиск и добавление товара/категории;
- `/account/profile`: смена пароля;
- отсутствие горизонтального overflow;
- текст в кнопках и таблицах не перекрывается.

## Проверка Технического Долга

Дизайн не оставляет намеренных временных решений:

- UUID остаётся внутренним значением API, но убирается из пользовательского сценария главной;
- полный список товаров решается через пагинацию, а не через увеличение карточек или скрытую первую страницу;
- дерево категорий не дублирует бизнес-правила backend, а улучшает выбор в UI;
- slug не становится магией: он видим, редактируем и валидируется backend;
- смена пароля ограничена текущим пользователем и не открывает контур управления пользователями;
- крупные frontend-файлы декомпозируются до добавления нового поведения.
