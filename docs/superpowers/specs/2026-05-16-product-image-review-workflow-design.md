# Product Image Review Workflow Design

## Цель

Сделать управляемый процесс подбора и загрузки изображений товаров по категориям. Процесс должен показывать найденные картинки в браузере через Playwright, давать оператору снять лишние выделения и только после подтверждения загружать выбранные изображения в локальное хранилище LineCom.

## Контекст

В проекте уже есть:

- `tools/download_tktdf_product_images.py` для trusted-source загрузки с `tktdf.ru`;
- manifest-формат для product image import;
- `LineCom.CatalogImport.Core.Images.ProductImageManifestReader`;
- Local FileStorage как целевой подход хранения файлов;
- админский API для ручной загрузки изображений товара;
- схема `stored_files` + `product_images`, где один физический файл может быть привязан к нескольким товарам.

Новый процесс должен использовать эти границы и не менять публичный дизайн каталога.

## Объем

Входит:

- обработка товаров партиями по одной категории;
- поиск кандидатов изображений в `https://www.tktdf.ru/`, `https://redmrt.ru/` и Google Images;
- браузерная витрина отбора с чекбоксами;
- машинная визуальная проверка Google-кандидатов перед предвыбором;
- сохранение выбранных картинок в PNG;
- manifest с источниками, checksum, статусами проверки и правовым статусом;
- применение выбранных изображений к товарам только после явного подтверждения.

Не входит:

- импорт цен, остатков, корзины, платежей или коммерческого текста с внешних сайтов;
- изменение карточек товара, публичного каталога, SEO-структуры или дизайна;
- утверждение юридического права использования внешних картинок;
- молчаливая замена уже загруженных изображений товара.

## Источники и лимиты

Для каждого товара собирается до 6 кандидатов:

- максимум 2 кандидата с `tktdf.ru`;
- максимум 2 кандидата с `redmrt.ru`;
- максимум 2 кандидата из Google Images.

Это не жесткая квота. Если источник дает мусор, документы, логотипы, баннеры, заглушки или нерелевантные товары, такие кандидаты не добираются ради количества.

Google используется как источник поиска и обнаружения исходных страниц/изображений. В manifest сохраняется фактический `sourcePageUrl` и `sourceImageUrl`; Google preview/CDN URL не считается надежным финальным источником, если можно получить исходную ссылку.

## Визуальная проверка

Для Google-кандидатов обязательна машинная визуальная проверка до предвыбора. Кандидат принимается к показу как отмеченный по умолчанию только если изображение показывает сам товар или визуально эквивалентную товарную группу.

Отклоняются:

- сертификаты, документы, PDF-превью;
- логотипы, иконки, баннеры, элементы интерфейса;
- упаковка без видимого товара, если она может ввести покупателя в заблуждение;
- близкий, но другой товар;
- слишком маленькие, пустые, битые или водянистые preview-изображения;
- изображения с явными признаками нерелевантного контекста.

Для `tktdf.ru` и `redmrt.ru` машинная проверка может использоваться как дополнительный фильтр, но итоговое решение остается за оператором в браузерной витрине.

## Браузерная витрина

Для каждой категории создается локальная review-сессия. Витрина показывает:

- название категории;
- карточки товаров;
- название товара, SKU/externalId, строку источника 1С, ключевые характеристики;
- найденные изображения;
- источник и ссылку на страницу-источник;
- статус автооценки и причину отклонения, если кандидат показан как невыбранный;
- чекбоксы выбора.

По умолчанию для товара отмечается до 2 лучших кандидатов. Первая выбранная картинка становится основной, вторая дополнительной. Если оператор снимает все выделения у товара, товар остается без новых изображений в этой партии.

После проверки оператор либо нажимает кнопку в витрине, либо пишет в чат команду на применение. До этого момента БД и Local FileStorage не меняются.

## Состояние отбора

Review-сессия хранит отдельные артефакты партии:

- `candidates.json` со всеми найденными кандидатами;
- `selection.json` с текущим выбором оператора;
- `review.html` или локальный review endpoint для Playwright;
- `manifest.json` после финального скачивания выбранных файлов;
- папку PNG-файлов выбранной партии.

Пути партии должны быть предсказуемыми, например:

```text
Assets/product-image-review/<category-slug>/
Assets/product-images/reviewed/<category-slug>/
```

Временные runtime-артефакты Playwright можно держать в `.codex-tmp`, но принятый manifest и PNG должны лежать в `Assets/`.

## Применение к товарам

Загрузка выполняется отдельным явным шагом после отбора:

1. Скачать выбранные исходные изображения.
2. Проверить, что файл декодируется как изображение.
3. Конвертировать в PNG.
4. Посчитать checksum.
5. Записать manifest.
6. Выполнить dry-run применения к товарам.
7. Если dry-run показывает ожидаемые назначения, применить к Local FileStorage и `product_images`.

Если у товара уже есть изображения, поведение по умолчанию:

- не удалять и не заменять существующие изображения;
- добавлять новые только если это явно разрешено для партии;
- не менять main image без явного разрешения;
- сообщать конфликт в отчете dry-run.

Для новой партии без существующих изображений первая выбранная картинка становится `isMain = true`.

## Manifest

Каждый выбранный item должен сохранять:

- `assetKey`;
- `productId` или стабильный идентификатор товара, если БД еще не применялась;
- `sourceRows`;
- `sourceSite`;
- `sourcePageUrl`;
- `sourceImageUrl`;
- `file`;
- `width`;
- `height`;
- `checksum`;
- `contentType`;
- `isMain`;
- `visualReviewStatus`;
- `rightsStatus`;
- `selectedByOperator`;
- `selectedAt`.

Для внешних изображений значение `rightsStatus` по умолчанию остается `requires-permission`, пока нет отдельного подтверждения прав.

## Ошибки и повторы

Сбой одного товара не останавливает категорию. Ошибки записываются в отчет партии:

- источник недоступен;
- изображение не скачалось;
- файл не декодируется;
- кандидат отклонен визуальной проверкой;
- товар не найден в БД;
- у товара уже есть изображение и замена не разрешена.

Повторный запуск той же категории должен уметь использовать существующие `candidates.json` и `selection.json`, чтобы не терять ручной выбор.

## Проверка

Перед применением партии:

```powershell
python -m json.tool Assets\product-image-review\<category-slug>\candidates.json
python -m json.tool Assets\product-image-review\<category-slug>\selection.json
python -m json.tool Assets\product-images\reviewed\<category-slug>\manifest.json
```

После реализации workflow также нужны тесты на:

- чтение и запись selection-файла;
- ограничение до 2 выбранных картинок на товар;
- сохранение первой выбранной картинки как основной;
- пропуск товара с существующими картинками без явного replace-флага;
- manifest-поля источника и правового статуса;
- фильтрацию документов, логотипов, баннеров и битых изображений.
