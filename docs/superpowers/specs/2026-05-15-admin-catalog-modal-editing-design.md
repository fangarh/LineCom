# Дизайн: модальное редактирование каталога и быстрая смена категории товара

## Цель

Улучшить удобство админки каталога: убрать постоянный боковой блок редактирования товаров и категорий, оставить спискам рабочую ширину и открывать редактирование в фокусных модальных окнах. Для товара должна появиться быстрая смена категории без открытия полного редактора.

## Scope

Входит в первый этап:

- Редактор товара открывается модально из строки товара и из действия `Новый товар`.
- Редактор категории открывается модально из дерева/строки категории и из действия `Новая категория`.
- Существующие вкладки редактора товара и поля формы категории остаются функционально эквивалентными текущим.
- В строке товара появляется компактное действие `Категория` для быстрой смены категории.
- Быстрая смена категории открывает небольшое модальное окно с деревом категорий.
- Быстрая смена категории разрешает выбирать только конечные категории, как текущий product category picker.
- Если смена категории может очистить или сделать неактуальными значения атрибутов товара, перед сохранением показывается явное предупреждение.
- Сохраняются текущие stale-request guards, CSRF-проверки, сообщения об ошибке/успехе и обновление списков.
- Фокусные тесты покрывают открытие/закрытие модалок, save/delete flows, быструю смену категории, предупреждение и обновление списка.

Не входит в первый этап:

- Массовая смена категории для нескольких выбранных товаров.
- Generated contract/OpenAPI infrastructure.
- Широкий редизайн админки вне products/categories.
- Новые возможности товара или категории сверх переноса редактора в модалку и быстрой смены категории товара.

## Рекомендуемый UX

Основной паттерн - модальное редактирование.

Списки товаров и категорий остаются на всю доступную ширину. Выбор существующей записи открывает модальное окно поверх списка, а не заполняет постоянную боковую область. Создание новой записи использует тот же modal shell. Закрытие модалки возвращает администратора к списку с сохранением фильтров, пагинации и контекста выбора.

Для товара модалка переиспользует текущую структуру редактора:

- Основное
- Атрибуты
- Изображения
- SEO
- Публикация

Для категории модалка переиспользует текущую форму категории. Существующие действия перемещения и сортировки должны либо остаться ниже основной формы в той же модалке, либо быть оформлены как компактная секция `Позиция`. Не нужно оставлять отдельный боковой блок перемещения категории.

## Быстрая смена категории товара

В строке товара появляется компактное действие `Категория` рядом с ячейкой категории. Оно открывает небольшую модалку:

- название товара;
- текущая категория;
- дерево категорий;
- предупреждение, если целевая категория отличается и существующие значения атрибутов могут быть очищены;
- действия `Сохранить` и `Отмена`.

Быстрая модалка должна использовать тот же backend update path, что и полный редактор товара, если к моменту реализации не появится более узкий endpoint. Команда должна сохранять текущие поля товара и менять только `categoryId`, чтобы операция была поведенчески эквивалентна изменению категории через полный редактор.

Если backend при смене категории очищает category-specific attribute values, предупреждение должно быть видно до сохранения. Быстрое действие не должно скрывать риск потери атрибутных значений.

## Структура компонентов

Предпочтительны небольшие переиспользуемые UI-компоненты, а не встраивание modal markup прямо в крупные managers.

Рекомендуемые компоненты:

- `AdminCatalogModal` - общий modal shell для catalog admin dialogs.
- `AdminProductEditorModal` - оборачивает существующий `AdminProductEditor`.
- `AdminCategoryEditorModal` - оборачивает `AdminCategoryForm` и controls перемещения/сортировки.
- `AdminProductCategoryQuickChangeModal` - фокусная модалка переназначения категории товара.

Managers остаются владельцами загрузки, mutation state, stale-request guards и обновления списков. Modal components получают состояние и callbacks; они не должны владеть API orchestration.

## Data Flow

Редактирование товара:

1. Администратор кликает строку товара.
2. `AdminProductManager` загружает detail товара.
3. Manager открывает product editor modal и заполняет существующий form state.
4. Save использует текущий create/update submit flow.
5. После успеха список обновляется, модалка остаётся открытой с сохранённым состоянием и success message. Это ближе к текущему поведению редактора, где контекст редактирования не исчезает после save.

Редактирование категории:

1. Администратор кликает категорию в дереве/списке.
2. `AdminCategoryManager` загружает detail категории.
3. Manager открывает category editor modal и заполняет form, move parent и sort order state.
4. Save/move/sort/delete переиспользуют текущие mutation paths.
5. После успеха списки категорий обновляются, модалка остаётся открытой с сохранённым состоянием.

Быстрая смена категории:

1. Администратор нажимает `Категория` в строке товара.
2. Manager загружает detail товара, если данных строки недостаточно для безопасной update command.
3. Открывается quick category modal с текущей категорией.
4. Администратор выбирает новую конечную категорию.
5. Если категория отличается, администратор видит предупреждение и подтверждает действие.
6. Manager отправляет update command, сохраняя текущие поля товара и меняя `categoryId`.
7. После успеха quick modal закрывается, список товаров обновляется, показывается success message.

## Accessibility и взаимодействие

- Модалка имеет `role="dialog"`, `aria-modal="true"` и связанный title.
- Escape закрывает модалку, если mutation не выполняется.
- Клик по backdrop может закрывать модалку только если mutation не выполняется.
- Initial focus попадает на title модалки или первое значимое поле.
- Закрытие возвращает focus к строке/действию, которое открыло модалку.
- Save/delete buttons disabled во время mutations.
- Alert/success messages остаются внутри модалки для edit flows и рядом со списком для quick category success.

## Тестирование

Frontend tests должны покрыть:

- строка товара открывает product editor modal;
- `Новый товар` открывает product editor modal с пустой формой;
- выбор категории открывает category editor modal;
- `Новая категория` открывает category editor modal с пустой формой;
- закрытие модалки сохраняет текущие фильтры и пагинацию списка;
- save товара всё ещё вызывает существующий update/create API с CSRF;
- save/move/sort/delete категории всё ещё вызывают существующие API с CSRF;
- quick category modal открывается из строки товара;
- quick category change запрещает parent categories и принимает leaf categories;
- quick category change отправляет сохранённые поля товара с обновлённым `categoryId`;
- warning показывается при смене категории товара с существующими category-specific attributes или attribute values;
- stale detail responses не заполняют закрытую или более новую modal session.

Manual QA нужен на desktop и narrow viewport, потому что старый side-by-side layout мог влиять на responsive assumptions.

## Отложенное решение

Массовую смену категории не включать в первую реализацию. После использования single-product quick category change решить, нужна ли bulk mode настолько, чтобы оправдать row selection state и дополнительные confirmation flows.
